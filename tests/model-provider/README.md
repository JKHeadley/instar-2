# Model-provider executable seam (rows 22/23)

`providerFixture` composes the public Five, Six, Seven, Eight, Nine and Ten factories over one signed, file-backed Part Two history and the physical content-addressed capture adapter. Five's fixture supplies its existing execution identity and a Six-authorized conditional writer; the production worker boot, supervision and credential-custody assembly remains outside this seam. This fixture does not certify production isolation.

The positive integration test performs Five pending step → Seven prepared capture → Eight immutable provider request → Six reservation/claim → Ten exact-byte HTTP submission → Seven receipt → Eight observation → real Nine assessment → Eight owner-view settlement → Six accounting → Seven bounded decision resolution → Five conditional acceptance. It checks one actual HTTP request, both wire hash and canonical digest, retained original object-valued occurrence Evidence, and no duplicate invocation. Eight's derived `operation-settled` fact field is only Five's existing settlement projection; Eight never regrades Nine's original Evidence or substitutes that projection into Nine's assessment.

The HTTP route owns an ephemeral credential in its closure, disables redirects/retries, and applies an abort deadline. The worker payload contains no credential, client or authority. Ten consumes Six's one-use claim and checks a persisted Eight executor-acceptance fact immediately before submitting the exact captured bytes. A caller-provided no-op acceptance callback is insufficient. A timeout, invalid return or missing receipt cannot release the consumed reservation.

`crash-worker.mjs` loads the compiled core in a separate Node process and is actually SIGKILLed after invocation before receipt, before assessment, before settlement, before accounting and before Five consumption. The parent reconstructs from durable files, checks the expected owner records and pending step, and observes zero replay calls. Unit and integration refusal fixtures exercise every refusal named by the brief, plus changed observations/vector, duplicate consumption and decisive non-occurrence with quiescence.

The additive public `effects/provider-api` entry point is also re-exported by the ordinary Eight index; cross-owner provider imports use that entry point so the unchanged pinned Eight-v1 compilation fixture remains valid.

The new Seven request and attempt kinds are separate from the unchanged version-one decoder. Provider requests, observations and settlements use distinct `effect-provider-*` fact kinds. Provider settlements persist the `ProviderEffectSettlement` body discriminator in its own Part Eight registration and expose the existing live `EffectSettlement` consumption view. Compose **all** original `registerEffectBodies` registrations beside `registerProviderEffectBodies`; no legacy migration or decoder replacement is installed. Legacy ordinary replies always use the original settlement kind and decoder, including when the additive Nine consumption path settles the reply after Five accepts a provider judgment.

The permanent independent-review cases live in `review/` and run through ordinary integration and E2E Vitest files. The additional eleven real SIGKILL cuts include Seven request/prepared, Eight request, Six reservation/claim/consume, executor acceptance, returned capture, Seven receipt, Nine request, and Seven resolution. Request-only recovery also rejects changed input and stale generation before completing the same durable preparation. Source Evidence captures are distinct per claim/operation; unavailable unrelated evidence remains unavailable and cannot change the affected operation's dependency closure.

The separate ordinary-reply integration test starts after Five acceptance and records its own Five pending step, message sourced from the accepted Seven resolution, request, Six claim, invocation observation, real Nine assessment, original Eight settlement and Six accounting. ## Round-2 integration blocker

The legacy decoder-preserving provider kind exposes a pre-existing coupling in Six: `settlementMatches` and `checkApplicationEvidence` accept only `effect-EffectSettlement`. Six therefore refuses the new provider kind before accounting. Provider credit release, Seven/Five acceptance, and the subsequent reply remain **unproven/red** until Six's owner adds support at both boundaries. This builder does not alter Six, rewrite signed kinds, or relabel these failed cases as passing.
