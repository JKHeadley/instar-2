Cause: `toolRoots` handed a file tool the SANDBOX's read set — `config.reads`, the system locations the kernel reopens so that a COMMAND can run at all (/bin, /usr/lib, /usr/share, /private/etc, /dev) — so a Read of /etc resolved to /private/etc/hosts, lay under one of them, and was ordinary work. w4-toolpaths (plan #442) had made that deliberate, to stop a readable file being refused for how it was spelled; it made every spelling agree by ADMITTING. This change keeps the spellings agreeing and makes them agree on a refusal: a file tool and a search now read exactly where they may write (the turn's workspace and the shell's temporary directory beside it), and a shell command that NAMES a path resolving under the host's own configuration is refused at admission, because that is the one thing the kernel cannot refuse at open — name resolution reads /etc/hosts itself, so closing it in the sandbox would stop every command that resolves a name. Both recorded shapes now come back decision deny, by every spelling and through a `..` escape.

## Closing block

simplestRobustRoute: the required outcome is that a tool call cannot read a file outside the agent's workspace, and that the refusal is recorded as decision deny. The simplest robust route is to delete the second read set: a file tool reads where it writes, decided on the resolved file by the function that already decides it (`place`/`toolRoots`/`resolvedPath`), so there is one set and no spelling crosses it in either direction. That alone fixes both recorded live failures, which were Reads. One bounded addition earns its place against a named failure the simpler route cannot prevent: the 2026-10-03 recording shows the same scenario reading the whole file through Bash, by a path the sandbox must keep readable, so a command that names the host configuration is refused too (`commandPaths`, one regular expression and one resolve per named path). Alternatives considered and rejected: (a) narrow the sandbox's read set instead — name resolution reads /etc/hosts itself, so the kernel cannot close it without stopping every command that resolves a name, and a Seatbelt change cannot be proved from this machine at all. (b) Add a sentence to the system prompt — that is willpower, and it changes the policy digest, which turns tools off on the live build until a successor activation record exists. (c) Judge every named path in a command against a reconstructed machinery allowlist — more machinery for no new refusal, since the sandbox already refuses those at open, and a real risk of refusing a command that names its own interpreter. Start guard: the check runs only on a path a command actually wrote out. End-state guard: the resolved path, never the spelling, decides. Limit guard: one root set, and the name check covers one root.
80/20: 0 must-fix, 3 notes. (a) The command-name check is name-shaped and so can be spelled around (a variable or a substitution); the sandbox remains the floor for that, and the leak it closes is the one the model actually wrote out. (b) The OPEN race between the hook's decision and the harness's open is unchanged and still only closable by running the harness as its own OS user (docs/defects/2026-10-03-file-tool-swap-race.md). (c) T2a passed in both failing rooms only because the first line of the hosts file is "##"; the content test would have caught a longer first line, so T2c was carrying the whole boundary. That is the check working as written, not a defect, and it is why the leak is treated as real here.
