# Change review — w4-testcap: the desk caps the workers of one full-test run

Subject base: 7964cd5a33d4132ce6dc58842e6508d6b861e89e
Review state: open
Reviewed content: none
Outcome: Two full tests running at once on the sixteen-core Studio ran twelve fork workers between them, saturated the host at 99% CPU and the agent's own session was reaped (observer #192, 17:21 2026-10-05). The worker count was a pure function of the host's CPUs, so a second concurrent run doubled it with nothing to say otherwise. Fix: `vitest.config.ts` reads an optional `INSTAR_TEST_MAX_WORKERS`, and the resolution is one pure function in `tests/setup/worker-limit.ts` — a positive integer gives `min(requested, host formula)`, so the cap only ever lowers the run; unset, blank, or anything that is not a positive integer keeps today's value exactly. `VITEST_SERIAL_GATE=1` still wins with one worker and no file parallelism, unchanged. An unusable value comes back named and the config writes one line to stderr, because a cap that silently does not apply is the saturation it was set to prevent. Evidence (this host: 10 CPUs, host formula 5): the new unit covers unset/blank, a cap below the formula (4 and 1 against 6, the desk case), a cap at and above it (6, 12, 4-against-2, 10^20 — never raised), and thirteen unusable values ('0', '-1', '-4', '4.5', '0.5', 'four', '4x', 'x4', '1e3', '+4', '4 4', 'NaN', 'Infinity'), each keeping the formula and naming itself back; a fifth case re-evaluates the real `vitest.config.ts` from a cleared module registry three times and reads its actual `maxWorkers` — 2 under a cap of 2, 5 unset, 1 under `VITEST_SERIAL_GATE` — so the three readings cannot be one cached copy. Two real runner invocations confirm the wired path: `INSTAR_TEST_MAX_WORKERS=2` runs clean, and `INSTAR_TEST_MAX_WORKERS=four` prints `INSTAR_TEST_MAX_WORKERS=four is not a positive integer; running 5 workers` and still runs. 52 tests pass across `tests/unit` plus `tests/assembly/production-grounding-checker-round4b.test.ts`, and `tests/transport/loop-main-head-mutation.test.ts` (3) passes — the two files beyond the unit folder that read `vitest.config.ts`. ## Closing block

simplestRobustRoute: the required outcome is that the desk can lower one full-test run's worker count without editing source between runs. The simplest robust route is the one this change takes: read one optional environment variable in the existing config — exactly how `VITEST_SERIAL_GATE` already works there — and resolve it with `min` against the formula already present, so the cap cannot widen the ceiling. A `--maxWorkers` flag on the desk's own command line was not chosen because the full-test command is `npm test` and the gate composes it, so the flag would have to be threaded through every caller; a lowered constant in the file was not chosen because it would apply to every host and every single-run gate. The one piece beyond the bare minimum is the two-field return and its stderr line, which prevents a named credible failure the bare number cannot: a typo in the desk's variable would leave the host at the uncapped count with no signal, which is precisely observer #192. Its cost is one `if` and one line of output on a path that is silent in every correct run.
80/20: 0 must-fix. 1 note: the cap is per run, so the number of concurrent runs remains the desk's to choose — nothing here bounds the host across runs, and two runs each capped at 4 still start 8 workers.
