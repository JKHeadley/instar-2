On 2026-10-05 the sb-w4-d1b full run hung from 07:12 to 08:02: one `scripts/test-intake-restart.mjs` child of tests/e2e/intake.test.ts sat at 0% CPU for 54 minutes and the whole gate waited on it. ## Closing block

simplestRobustRoute: the required outcome is that a test child which blocks forever fails its own test quickly and legibly instead of freezing a whole gate run, and that this holds for every synchronous child call rather than the one that happened to hang. The simplest route that delivers it is one interception of the one call all three synchronous APIs already funnel into, with the bound read from state the runner already keeps (the case's own declared timeout). That is what is built: one setup file, three exported pure helpers, no new store, service, script, inventory or register row, and no change to the harness that hung. Two simpler-looking routes were tried or considered and are recorded as decisions above: editing the 202 unbounded callsites by hand (unverifiable inside this unit, and silent for every future callsite) and patching the child_process module's exports (tried first, and WRONGLY rejected: the attempt omitted `syncBuiltinESMExports()`, so the named imports really were unbounded, but the supported publish makes that route work and the repair commit takes it). The added machinery beyond the injection is the stderr line; the named failure it prevents is a hung case being reported only as a bare "Test timed out in Nms" with no indication that a child blocked — the diagnostic gap that cost 54 minutes. (The deprecated-binding guard this field also claimed is gone with the private binding itself, in the repair commit.) Guards: the start guard is that the doorway acts only inside a vitest worker (it is installed by `setupFiles`, never by product code) and only on a call that named no `timeout`, so a caller-owned bound and every non-test process are untouched. The end-state guard is that the child is dead (SIGKILL) and the call raises `ETIMEDOUT` with the explanation also on stderr, and that the patch is idempotent behind `Symbol.for('instar.tests.boundChildren')` so a re-import cannot double-wrap. The limit guard is the bound itself — the case's own declared timeout, or the finite 300 s collection-time fallback, with `INSTAR_TEST_CHILD_BOUND_MS` as the only widening knob and no path to an unbounded wait except a callsite deliberately writing `timeout: 0`.
80/20: 0 must-fix. Three notes carried into the report. (1) 201 callsites remain without an explicit per-site timeout and are bounded only by the doorway; that is deliberate, and tests/unit/bound-children-installed.test.ts asserts the doorway reached the worker so the coverage claim rests on wiring rather than on an import the test performed itself. (2) The bound usually surfaces as vitest's own timeout verdict rather than the raised error, because it lands on the case deadline; the stderr line is what names the child, and a per-callsite timeout tighter than the case budget (as intake now has) is what makes the raised error the verdict.
