Outcome: The gate's one failure was `tests/integration/resource-owner.test.ts > does not hold a tree process ceiling: with baseline churn and a concurrent launch, a tree can exceed it` — `expected 4 to be greater than 4`, flaky on live L49 at 6 pass / 5 fail. The product behaviour it asserts is correct and unchanged: a launch's process ceiling becomes the kernel limit of the whole user ID (`processLimit()` in scripts/resource-owner.mjs: the uid's live `ps -U` census plus `ceilings.launch.processCount`), so it is never a tree bound, which is exactly what this case proves. The defect was in how the case created the room a tree grows into. It freed twelve same-user processes and then trusted two fixed sleeps — 700 ms for both launches to have anchored their limit, 200 ms for the freed processes to be reaped — and let two trees fork into the shared room at once. With roughly six of those twelve slots taken by unrelated same-user work from the parallel suite, 8 of the 16 requested forks were refused and the two trees split the rest evenly: max started was exactly 4, the ceiling itself, and a true claim read as false. Four changes make the room provable rather than hoped for: the baseline is 32 processes, wider than the churn a parallel suite adds in the same second, and the room is asserted present (at least 24 live pids) so a host that refused the spawns reads as a failed setup, not a failed proof; each launch's tree writes a ready file as its first act, and the churn waits for both, so the churn provably happens after both limits were set (the shim applies `ulimit -u` before it execs the launch, so a running tree means an anchored limit); the baseline exits are awaited through their `exit` events instead of slept on, because a zombie still counts against the user-ID limit it was counted into; and the two gate files are written 500 ms apart so one tree forks into the freed room alone and the proof never rests on how two trees split it. The launch timeout for these two launches is raised from the helper's 15,000 ms to 20,000 ms, because the ready wait is now bounded at 10,000 ms and the old sleeps were 900 ms. Layer below: the kernel semantics this proof stands on. On macOS, RLIMIT_NPROC bounds processes per user ID, which is what `processLimit()`'s `ps -U` census plus ceiling assumes, and `/bin/sh` is bash, whose `ulimit` accepts `-u`. Both assumptions were checked for this repair and both are macOS-only: on this Linux host `/bin/sh` is dash, whose `ulimit` rejects `-u` (the shim exits 125), and when the shim is run under bash instead, RLIMIT_NPROC bounds *threads* per user ID, so the launched node aborts in `uv_thread_create` before it runs. Every case in this file therefore fails on a Linux host for reasons no case in it is about, which is why this repair's own assertion could not be re-run here and is verified on the gate host; the four mechanics the repair adds were each verified directly on this host instead, and the evidence is in the report.
