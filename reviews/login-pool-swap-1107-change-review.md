# Change review — hold a login its CLI reports signed out, so the next turn runs on another approved login

Subject base: 3ad4ec04e38b820c2e715c02fe73df9c1028abf3

Outcome: when an approved Claude login in the runner's pool is signed out, the next turn runs on another approved login with room, without a restart and without a new message to the operator. 1.x (JKHeadley/instar 1a5def9c9, src/core/QuotaPoller.ts:176-215, 490-500, 701) moves an account to needs-reauth on the CLI's own signed-out evidence and holds it while the stored credential is the same one the CLI refused; a changed credential or a 12-hour ceiling releases it, and the scheduler selects another account. 2.0 already switched on usage thresholds and typed provider limits (tests/preview/harness-login-pool.mjs select/observe, the "switched to the next approved login" notice), but learned signed-out only from a 1.x usage document's needs-reauth status (harness-login-pool.mjs:275 at the base), which its live quota reader never reports (scripts/claude-pool-quota.mjs:90 writes only active/unknown). A signed-out login therefore stayed selected and every turn failed on it. This change ports the 1.x hold into the pool and feeds it from the CLI's own two exact signals.

The move is recorded as a `member-unavailable` switch (no person-facing line, as for every member-unavailable move) and the existing sign-in repair item names the account for the desk. The outage view skips a held signed-out login like a needs-reauth one, so when every login is signed out the one fixed outage notice states no reset time. State validation accepts the new hold reason only with an integer reset and a fingerprint or null.
