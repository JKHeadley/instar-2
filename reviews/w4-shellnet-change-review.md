Outcome: The sandboxed shell gets network reads through a checkpoint instead of no network at all (plan row #419; the purpose's revision 12, Justin, topic 102965 message 122028: ability is never reduced to satisfy a safeguard a checkpoint can enforce). (1) tests/preview/egress-checkpoint.mjs: one process per tool turn, the sandbox's httpProxyPort and its only reachable address; it mints a per-turn TLS authority (EC key in the admission state, certificate on the scratch volume, one-day validity) and terminates each HTTPS tunnel, so it sees each request's method and full URL. Each request is decided by admitEgress: GET, HEAD and git's fetch negotiation (POST .../git-upload-pack) of a public host on ports 80/443 are ordinary reads; every other request (other methods, git push discovery and upload, publishes) is a network write sent to the effect doorway's admitToolEffect, refused unless the profile registers tool:network-write, answered 403 with the reason. Names are resolved at the checkpoint and only a checked address is dialled (loopback, private, link-local, shared, mapped IPv6 and names resolving to them refused); each decision, with its addresses, is appended to the admission record before the request leaves; bounds: 16 open requests, 512 requests, 256 MiB down, 8 MiB up, 30 s idle, its own 330 s lifetime; it adds no credential or header of its own; an internal error fails that request only, counted. (2) tests/preview/tool-turn.mjs: runToolTurn starts it after the reservation and before the harness, records its port in the admission config, hands the port and the toolchain reads to the launch, stops it by its exact process id after the harness ends, and journals network/egress/egressOmitted/egressErrors; if it cannot start the shell runs offline and the trace says why; toolchainReads offers the runner's node installation and the developer tools holding git. (3) src/assembly/production-provider.ts: settings template v2 sets sandbox.network.httpProxyPort and allowRead for the toolchain (validated: port range, at most 8 plain paths, none covering the hook, the state, the home or a denied root); the tools sentence says how the shell's network works. (4) tests/preview/tool-admission.mjs: toolShellPrefix exports the trust-root and proxy variables (by address: node cannot resolve localhost in the sandbox), DEVELOPER_DIR and PATH for the toolchain, skips git's system and home config, and gives git clone/init a separate git directory on the volume because the sandbox (rightly) refuses .git/config and .git/hooks writes; toolTrace reads egress rows. ## Closing block

simplestRobustRoute: required outcome: curl, git clone and package installs from the sandboxed shell, with writes, this machine and credentials still held. The simplest robust route is the harness's own bring-your-own-proxy setting (httpProxyPort) pointed at one small per-turn proxy that terminates TLS and applies the existing doorway and public-address checks; per-tool adapters (option b) would cover only named tools (curl would still fail) and add a wrapper per client, so they are not simpler for the required behavior. The added machinery prevents named failures: without TLS termination a POST over HTTPS is indistinguishable from a GET (the reason w4-toolsfull kept the shell offline); without resolving at the checkpoint a name could point at this machine; the per-turn authority, rather than a standing one, means nothing it signs outlives the turn. Start guard: checkpoint start failure leaves the shell offline (recorded). End-state guard: stopped by exact pid with the turn, its lifetime as backstop. Limit guards: requests, concurrency, bytes, idle. Unattended shipped-path result: two real pinned-harness turns (scripted model endpoint) through runToolTurn, hook, sandbox and checkpoint.
