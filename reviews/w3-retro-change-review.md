# Change review — w3-retro: the retrospective review asks for an answer bigger than the route's output cap, so no pass can ever complete

Subject base: 30bda628294c58d04c895b67460e2ef94af1f084
Review state: open
Reviewed content: none
Outcome: No live retrospective pass has ever completed: in all ~1,400 recorded proof-room and preview status snapshots from 2026-09-29 to 10-01, `ports.retrospect` returns `uncertain` and journal.ts records `unknown: model outcome uncertain`. Cause: the subscription provider refuses a result frame whose reported output exceeds `policy.maxTokens` (2048) and retains that outcome as `uncertain` (production-provider.ts: `ensure(... frame.usage.output_tokens <= policy.maxTokens ...)` inside the `catch { return uncertain(); }`), and the review's required answer is always over that cap. CLAUDE_CODE_MAX_OUTPUT_TOKENS does not bind the CLI, so the model simply writes more. The live record proves the mechanism exactly: the 2026-09-29 room has 18 `call-outcome` rows with `localLimit: 'output-cap'` at 2229-8192 output tokens and exactly 18 `summary-uncertain` rows carrying those same token counts, while every reply (454-1239 tokens) stayed under the cap and completed. Measured here, a pass over 14 operator messages plans 28 cases whose MINIMAL valid answer is already 7011 bytes and whose realistic answer is 11923 bytes; at the measured 2.7 bytes per output token (the only two verbatim live outputs on record are 1616 bytes at 600 tokens and 2119 at 716) both are far over 2048 tokens. Fix, in three parts: the plan now bounds a pass by the answer it asks for as well as the packet it reads, deferring the cases that do not fit exactly as an oversize packet case is deferred (they stay owed); the question states that budget and the per-field lengths it implies; and a pass whose own `call-outcome` row proves an ended call with a result frame over the cap is settled `failed` with the named reason `review output over the cap` instead of `unknown`, which both tells the truth and narrows the next pass's budget (halving, floor one case) so a wrong estimate converges instead of repeating an unanswerable ask. Evidence: tests/preview/retrospective-over-cap.test.ts (6 tests) replays the real recorded over-cap outcome rows and uncertain usages from tests/preview/fixtures/proofroom-summary-cascade-stall-2026-09-30.json, shows the settled-failed reason on both the exit-0 and the exit-1 is_error frame, shows both negative sides (uncertain with no over-cap row stays `unknown`; an unended call or a non-result frame is not read as over-cap), and shows a pass completing with findings, grades, every duty and every gravity well judged, with its answer inside the cap and its deferred cases picked up by a later pass. tests/preview/retrospective.test.ts (33) and tests/preview/retrospective-live-shapes.test.ts (2) pass.
Affected rules: 24 (a repair that keeps running and keeps failing: the recurrence was the bug, and it was invisible because every pass recorded UNKNOWN), 50 and 51 (the retrospective is the holder for Friction Is a Spec and Notice + Solve Inefficiencies; neither could be proven because no pass ran), 2 (an over-cap pass is now a named settled failure, not a silent unknown; deferred cases stay owed and are picked up on age), 42 (the refusal stays a refusal: a pass still records no grade, finding or candidate, and the uncertain-with-no-evidence case is still UNKNOWN, never promoted to a failure it cannot prove), 26 (the over-cap verdict is read from the pass's own recorded physical outcome row, not from the error flag or the exit code), 95 (the declared fail direction for this consumer is unchanged: discard, every case stays owed), 13 (the byte budget binds its subject: bytes per output token is measured from the two verbatim live outputs on record, not assumed), 116 (one extra bound in the existing case loop, one estimate, one reason constant and one existing-signal read; no new store, format, service or model call)

## Closing block

simplestRobustRoute: bound the ask instead of widening the route. The required outcome is a retrospective pass that completes and records its findings; the route's output cap is the wall, and the only two ways past it are to raise the cap or to ask for less. Raising it means changing `policy.maxTokens`, which changes the invocation-policy digest and so requires a new signed activation record — operator-held machinery, for a wider resource bound, to make one consumer fit. Asking for less reuses what the design already has: the plan already defers a case that will not fit its packet bound and records it as owed, so the answer bound is one more term in that same loop; the question already carries the review's instructions, so the budget is one more line in it; and the summary consumer already settles this exact provider bound as a named failure and narrows its next ask, so the retrospective follows that proven path rather than inventing one. The added machinery is the estimate and the narrowing, and each prevents a named failure the simpler route cannot: without the estimate the first pass, and every pass after a complete one, burns its single model attempt on an ask the route will refuse (the live defect); without the narrowing a drifted estimate repeats that forever with nothing recording why (the live defect again, one layer up). Both are read from the journal's own records, so neither adds a store, a format, a service or a model call.
80/20: 0 must-fix. Notes: (1) the mandatory fixed part of the answer — 14 duty rows and 7 gravity wells — is about 2.6 KB of the 4.7 KB budget, so a more compact answer schema would roughly double the cases per pass; that is a separate unit, and it changes the wire format the validator decodes. (2) A pass now covers about four operator messages, which is what a 2048-token cap allows; whether the cap itself is right for this consumer is an operator question about the activation record, not an engineering default, and it is not raised here because the fix does not need it.
