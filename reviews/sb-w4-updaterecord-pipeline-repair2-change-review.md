## Closing block

simplestRobustRoute: the required outcome is that this test stops failing for a reason unrelated to what it tests, without giving up any of what it asserts. The simplest robust route is two numeric arguments in the one test that failed: give the call's arrival enough room that a stalled shared event loop cannot abort it before it reaches the provider, while keeping the driver timeout under the admitted bound so the narrower-value claim survives. No helper, no flag, no new check, and no change to any shared fixture. Alternatives considered and rejected: (a) recording the request at handler entry in http-provider.ts — my first hypothesis, refuted by measurement (entry and body-read completion agree in every run), so it would be machinery against a failure that does not occur; (b) reworking the fixture so the abort fires on an explicit signal after an arrival promise resolves, which is genuinely deterministic — it adds a hook to a fixture 17 files share and would stop the test proving that the *admitted timeout* caused the uncertainty, which is half its name; (c) relaxing the assertion to a before/after delta on `requests` — deterministic and smaller, but it silently drops the "reached the provider once" claim; (d) replacing the timeout with a server-side uncertain response — that is a different scenario from a transport timeout and would quietly delete the `transport-threw` coverage; (e) quarantining it under Rule 37 — refused, because a source fix existed; (f) widening the sibling case too — rejected, because its budget is the admitted bound itself and 17 files share the definition that sets it. Honest residual, stated rather than implied away: with client and server on one event loop, no budget is deterministic; 90ms is a measured 4× improvement at the stall sizes that actually broke it, not a proof.
