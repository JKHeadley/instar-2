Outcome: Plan row #439. Instar 2.0 had no operator dashboard, so Rule 81 read UNTESTED (Q81 NEEDS-FEATURE). This adds the first slice. The dashboard is a page of the independent approval page (scripts/approval-surface.mjs), the operator's own process, at /TOKEN/dashboard. Nothing from the agent shows until the operator's enrolled passkey signs in, with one assertion over a fresh nonce whose signed bytes are a different type from any act (signInChallenge). A sign-in therefore never stands for an approval, and an approval never opens a session. After sign-in it shows the agent's status (the exact chat status answer), the requests waiting for the operator with a direct link to where each is answered (the approval page, the GitHub review or the chat), the last 10 messages with what happened to each, the allowance used, and the stop (a link to the page's own standing Stop). Approve, decline and stop are never performed on the dashboard itself. The runner publishes one disposable snapshot into its own approval outbox (tests/preview/operator-dashboard.ts), at most every 15 seconds and once at exit. The snapshot is built from the journal by the functions the status reply uses (statusAnswer, turnsToday and heldReplies, extracted from statusReply, plus operatorRequestsReport), so there is no second source of truth. The page treats the snapshot as untrusted data: it accepts only a closed, bounded shape whose only links are a GitHub review page or the operator's chat, escapes every field, shows the snapshot's age, and says plainly when the snapshot is missing, unreadable or stale. scripts/check-dashboard-floors.mjs checks Rule 81's eleven floors on any tree. Each floor has a negative control that must turn it red and a population count. The script also checks that nothing is exposed without the passkey. It is the command live-proof Q81 can run on the deployed tree.

## Closing block

simplestRobustRoute: the required outcome is one phone page, behind the operator's existing credential, that shows the facts the status reply gives, the requests waiting with their direct links, recent messages, the allowance and the stop, held by Rule 81's eleven floors. The simplest robust route reuses three existing mechanisms: the approval page process (its ingress grant, its loopback listener, its passkey and its standing Stop), the runner's existing outbox to it, and the status reply's own functions. The added machinery is a typed sign-in challenge with an in-memory session, which prevents the dashboard showing message excerpts to anyone holding the link, and one snapshot file. That file is needed because the operator's process cannot read the encrypted journal, and giving it the key would break the identity split. A server in the runner was considered and rejected: it would need its own ingress grant, it could not use the operator's passkey on another host, and on the same host it could script the approval page. The floor check is one script, with a negative control per floor, so Q81 cannot pass on a matcher that matches nothing.
