Outcome: unit review of w4-intaketimeout (Astra, round 2) returned VERDICT: NO on one must-fix, M2. The doorway picked the options argument with `Array.isArray(args[1]) ? 2 : 1`, which reads every non-array second argument as the options. Node also accepts `spawnSync(file, undefined, options)` and `execFileSync(file, null, options)` — the arguments array omitted, the options still third — so on those shapes the wrapper injected its bound into second position and discarded the caller's real options. Reproduced here first, on this host's node 22.23.2, against real children: the original `spawnSync(execPath, undefined, { input: 'process.stdout.write("ok")', encoding: 'utf8', timeout: 2000 })` returns `'ok'` and the wrapped one returned an empty buffer; the original `execFileSync` with the same arguments returns `'ok'` and the wrapped one threw `ERR_INVALID_ARG_TYPE` ("callback" received an Object), because Node's `normalizeExecFileArgs` takes the injected object as the options and then the caller's real options as the callback. Both reproduce with `null` in second position as well. Fixed at its source: `optionsSlot` now decides by what second position HOLDS — a non-array object IS the options, and an array, an omitted array (`undefined`/`null`) or anything else leaves them third — and it is told whether the call has an arguments array at all, since `execSync(command[, options])` has none. The regression is asserted against real children in tests/unit/bound-children-probe.mjs (a real fresh process, real ESM named imports): with the fix the omitted-array call returns `'ok'` through both `spawnSync` and `execFileSync`, an omitted-array call that names no timeout is still killed at the 1200 ms bound with the named explanation, and one that names its own 300 ms timeout in that third position is honoured as written rather than raised as the bound. Both sides were proved: with the selector reverted to `Array.isArray(args[1]) ? 2 : 1` those cases and the `optionsSlot` case fail (5 failed / 22 passed); with the fix all 27 pass. Nothing else about the doorway changes — the timeout selection, the explicit-timeout pass-through including a deliberate `timeout: 0`, the SIGKILL, the stderr diagnostic, the named error and the five intake callsites' own 20 s bounds are untouched.

## Closing block

simplestRobustRoute: the required outcome is unchanged and so is the doorway: one wrapper per public synchronous child call, injecting a finite bound where the caller named none. The only question this repair asks is which argument that bound goes into, and the simplest thing that is actually right is to read second position for what it holds — object, array, or omitted — and to be told, once per wrapper, whether the call has an arguments array at all. The routes rejected: calling Node's own normalisation first, which is not exported and would mean re-implementing it anyway; normalising the arguments into a canonical shape before forwarding, which would change the call every test wrote rather than only the options slot, and would have to invent an answer for the shapes Node refuses; and restricting the doorway to calls that pass an arguments array, which would quietly unbound every options-only callsite and is the ability-narrowing route the purpose document rules out when a checkpoint can do the work. Guards: the start guard is unchanged — the doorway acts only inside a vitest worker and only on a call that named no `timeout`. The end-state guard is that the caller's options reach the child, asserted on the child's own output through both affected calls, and that an explicit third-position `timeout` is still passed through byte-for-byte, asserted by object identity against a stub and by a real 300 ms kill in the probe. The limit guard is the bound itself, unchanged: the case's own declared timeout or the finite 300 s collection-time fallback.
