Outcome: Live replies increasingly settle "send-unknown" and an UNKNOWN send is never retried (the no-duplicate floor), so the operator may never get the reply and every proof run that hits one waits its full 16-minute reply timeout (room two 2026-10-02: 4 of 58 — updates 6230937, 6230973, 6230987, 6230989, each with no recorded send latency and no message in the chat; group S lost about 30 minutes to two of them). Two defects. (1) Classification conflates two different things: the transport returns the same `{kind:'uncertain', stage:'child-exit'}` whether the child was killed mid-flight (may have delivered) or never ran at all (provably delivered nothing) — the limit shim's `exit 125` (scripts/limit-exec.sh) and the bridge's `process.exit(2)` both precede their `exec`/`fetch`, and `spawnSync` reports a host refusal to start the child in `error`. That exact fork failure has already been seen live: the shim's own ordering comment records "a count that rose since it was read made that fork fail: a sent message read UNKNOWN". Reproduced here with the real production transport: on a host whose /bin/sh cannot apply `ulimit -u` the shim refuses with 125 and the send was recorded UNKNOWN. (2) The recorded reason was readable only by decrypting the journal: every operator view said "unknownSends: 4" and nothing more, so the cause of a lost reply could not be read at all. Fix: `settle` reports the two provable pre-network refusals as `spawn-refused`/`launch-refused` carrying `sent: false`; `classifyTelegramSend` maps `sent === false` to a new transport-only `not-sent` outcome; the one outbound funnel dispatches that exact signed intent once more (nothing reached Telegram, so no duplicate is possible) and records a second proof as `refused` with its reason, never UNKNOWN; and `sendOutcomeCounts` projects `unknownReasons` (counts by reason) plus `lastUnknown`, which `status` already spreads. Everything that MIGHT have delivered — fetch-timeout, fetch-failure, child-exit, body-read, a 5xx, a receipt that differs — stays UNKNOWN and is still dispatched exactly once. ## Closing block

simplestRobustRoute: the required outcome is that a reply which provably never left this machine reaches the operator instead of being silently abandoned, and that the desk can read WHY an UNKNOWN send is unknown without decrypting a journal. The simplest robust route is to have the transport state the one fact only it knows — whether the network call was made — in its existing closed reply shape, let the existing single outbound funnel act on it, and put the already-recorded reasons on the status pull that already spreads those counts. Added machinery: one exit-code set and one boolean in the transport, one outcome kind the funnel consumes and never stores, one bounded extra attempt, and two derived status fields. A general retry policy was not taken: it would have to decide retryability for outcomes that may have delivered, which is exactly the no-duplicate floor. Lengthening the 30-second send deadline was not taken: measured live send latency on that root was 673-1765 ms, so the deadline is about seventeen times the slowest real send and is not the constraint. Guards: the start guard is `sent === false` asserted by the transport itself (a missing, true or non-boolean field is never proof); the end state is one of the three journal outcomes; the limit is one extra attempt, bounded by a named constant.
