## Closing block

simplestRobustRoute: the required behavior is (a) a durable work item or scheduled job launches a full harness session with ownership, a stop, caps and its result in the journal, and (b) a root configured for Codex actually runs Codex for answers and work. The simplest robust route is this proposal, and it is deliberately thin: one port over the EXISTING session driver (no new scheduler, no new job kind, no second journal), two optional ports on the existing worker interface that mirror the `toolRoute`/`model` pair already there, the existing `obligationDecision` reader for the session's answer, and one adapter module plus one registry entry behind the doorway interface that already existed for exactly this. Each piece of added machinery prevents a named failure the simpler route cannot: the result-file stability gate exists because the pane-idle classifier demonstrably never fires on the live Codex TUI (a finished step would hang to its deadline); the per-launch step ceiling exists because a repeatedly failing step would otherwise launch sessions without end (Rule 61); the tool-item refusal exists because `codex exec` has no no-tools flag, so without it an answer could be produced by a run that also changed something; the auth-mode observation exists because `codex login status` cannot distinguish a subscription from an API key, so without it the subscription-only floor would rest on nothing; the window module exists because the import cycle it removes actually threw. The simpler route NOT taken: driving the session from the pane only (rejected — the classifier is per-harness and silently wrong here), and a second doorway registry or a per-harness branch in the runner (rejected — Rule 30 already gives one interface, and the runner now selects through it instead of naming a harness).
80/20: 0 must-fix. Three notes. (1) The Rule 115 native harness contract has NOT been run against the Codex doorway and is deliberately not claimed: both new tuples are UNPROVEN with that reason, and the native harness is named as the next row (the brief's instruction, not built here). (2) Three tests cannot run on this host and are named rather than worked around: the shipped Rule 60 limit shim needs a /bin/sh with `ulimit -u`, which dash does not have, so it correctly refuses (exit 125) and every provider-spawn case fails here — pre-existing, verified on the untouched base; the two `native-harness-contract.test.ts` confinement cases need macOS `sandbox-exec`; and `shipped-clients.test.ts` asserts the self-host tuple's certified runtime equals the running one, which is the Studio's node-24.14.1 and not this host's node-22.23.2 (the same single pre-existing architecture finding the baseline carries on this machine). (3) The session work path is reachable only when a root is configured with the five `--session-work-*` options; no live root is, so this lands dark by configuration and the Studio should run the shim-complete gate. (4) A delegated session is UNCONFINED and its effects are not classified by the effect doorway, which is not on the live path on this HEAD (plan row #400). That is now stated in Part fifteen §5 as a Rule plus an explicit Value and in Affected floors above; it is the one thing to weigh before configuring any root for session work, and it is the reason this path should stay unreachable until that doorway lands.
