Outcome: Plan row #404 (the operator's 2026-09-13 direction): when the agent fails to remember something it should have, the failure is recorded durably with what was asked, what the memory path returned, what the truth was and the stage the evidence points at — and what is recorded changes the next recall, rather than only being counted. (1) tests/preview/memory-learning.ts: one new module of pure functions over the journal's own projection. `memoryFailures` reads each operator correction of an agent reply beside that reply's own recorded `ReplyGrounding`, and classifies the stage strongest-evidence-first as not-retrieved, summarized-away, never-stored, wrongly-stored, or undetermined where the evidence names none. `memoryFailureCues` turns the words that failed to reach a record into that record's own derived index terms; `applicableCues`/`memoryFailureCuesFor` apply a hint only to a question that substantially repeats the one that failed. `memoryLearnings` promotes a cause that has happened more than once into a fixed standing note. `memoryFailureStatusLines` is the pull reading. (2) tests/preview/journal.ts: `ownedRecall`, the one recall owner every retrieval path already goes through, merges the applicable hints with the write-side meaning index before `composeRecall`; the answer packet carries `memoryLearning` for a verified operator turn once a cause recurs. (3) tests/preview/status-command.ts: the status reply carries the memory-health lines. Nothing is stored beside the journal: replay rebuilds every value above from rows that already exist, so a failure survives a restart because its evidence does.

Tier rationale: the change adds no authority, no effect and no model call — it is a read over the journal's existing projection plus two read-only additions to paths that already exist. But both of those paths feed the answer to a person, and a message to a person that changes what they know is a consequential effect by the purpose's own definition, so a pipeline the reply depends on is critical. The one way it can harm is by displacing a correctly recalled record; that risk is measured against the realistic-recall corpus and carried in the side-effects and 80/20 sections.
Side effects: `ownedRecall` now merges failure-derived cues into the candidate cue lists; with no applicable hint the candidate objects it builds are byte-identical to before, so a journal with no recorded memory failure ranks exactly as it did. The answer packet gains a `memoryLearning` array for a verified operator turn once a cause has recurred (absent otherwise, so no existing packet changes size). The status reply gains one unconditional line and two conditional ones; the unconditional line names how many corrections lie behind the read bound when any do. No journal frame kind, view field or stored byte changes; a journal written before this change replays identically. Measured regression risk: an unscoped hint displaced one needed record in the 300-turn realistic-recall corpus (57 → 56 present); the fix is that a hint applies only to a question that shares at least half its words and never fewer than two, and that a correction of a stored record never produces a hint at all — the record it names is the superseded one. With both, the corpus is back to 57/57 and 14/14.
Undo and recovery: revert this change and this record. Nothing persists outside the journal, so a reverted build reads the same journals with no migration and simply stops deriving the failures and hints; no root can be left in a state the reverted build cannot open. To keep the recording and drop only the behaviour change, delete the `memoryFailureCuesFor` merge in `ownedRecall` and the `memoryLearning` packet block; the status lines and `memoryFailures` are read-only and safe to keep.
Multi-machine posture: machine-local by construction, and deliberately so. Every value is derived from the journal the owning runner holds, so a machine that takes a conversation over replays the same rows and derives the identical failures, cues and notes — nothing to replicate and nothing that can diverge. There is no cross-machine state, no new file and no shared cache. On a single-machine installation this is the whole of the behaviour.
Layer below: `ReplyGrounding` and `continuityFrontier` (read, unchanged — this change depends on the grounding recording what the packet actually carried, which journal.ts already verifies against the packet before returning it); `MemoryChange` and the memory decision path (read, unchanged — the model's `in: 'reply'` correction is what this reads as the failure signal, and its `offered`/quote validation is what makes the signal trustworthy); `meaningTermsIndex` and `view.indexConcepts` (read, never written — the write-side index and its coverage reading stay exactly as the summary writer left them); `composeRecall` (unchanged — the cue list is its existing input; its derived stage scores only candidates whose cues match, so a non-matching hint adds nothing to the order); `turn.lookup` (read, unchanged); `view.conflicts` (read only as the reason this change does not also read contradictions: the journal already detects one, asks the operator and records a winner).

## Closing block

simplestRobustRoute: the required outcome is that a memory failure is recorded with its evidence and then changes behaviour structurally. The simplest robust route is to derive it from what the journal already keeps and to repair it through the mechanism that already exists, and that is this route: the operator's correction is already a durable `MemoryChange` the model decided; the answer's own `ReplyGrounding` already records exactly what the packet carried and which frontier hid the rest; the derived meaning index already exists as the channel through which a record is reachable by words it does not itself use; and `ownedRecall` is already the one adapter every retrieval path calls. So no new store, frame kind, sentinel, runner tick, model call or schedule is added — three read-only additions to existing paths and one module of pure functions. Added machinery, and the named failure each prevents: the hint match floor (an always-on hint displaces a correctly recalled record — measured, 57 → 56 on the realistic-recall corpus); the refusal to hint from a record correction (it would promote the superseded value); the `undetermined` cause and the carried-record test (they prevent a correction that is not about memory from being counted as a memory defect, which would both mislead the reading and fire a standing note at the model for no reason); the bounds (an unbounded cue set would grow the derived index for the life of a conversation), and the newest-first read bound with its named remainder (an oldest-first bound would make a conversation silently stop learning at the exact point it had made enough mistakes to need to — found by a scope re-read, not by a test). Start guard: a correction only enters when its answer recorded a grounding. End-state guard: the failure is readable on the status surface and in the packet, and its evidence fields are what a reader checks it against. Limit guards: the newest 200 corrections read with the remainder named, 32 cue sources, 12 terms each, 2 standing notes. Unattended shipped-path result: the recorded proof-room-two miss of 2026-10-02, replayed through the shipped packet and recall path, produces the recorded failure and then recalls the record it missed; the full Telegram live proof is the desk's, not run here.
80/20: 0 must-fix, 4 notes — (1) a contradiction between memory and the journal is deliberately not read here, so the direction's fourth trigger is covered by the existing conflict machinery rather than by this unit; (2) the `undetermined` cause means a correction after a complete-history answer is counted but not diagnosed, which is honest and also means the count is an upper bound on memory failures rather than an exact one; (3) the hint is derived from the failing question's words only, so a record that is missed by a differently-worded question a second time earns a second hint rather than a better one; (4) the standing note is advisory text in the packet — the model may ignore it, and nothing here measures whether it changed an answer, which is Part 20's join to build.
