# File-tool race between admission and open (secrets floor)

**Status:** CLOSED for exactly three things, and nothing more is claimed. (1) The operator account's private files: closed by the kernel when the harness runs as its own macOS user (`--harness-user _instarharness`; desk unit harness-user, plan row #464, merged for plan row #470), because every open is checked as a user that cannot read or write them. (2) Credentials as files the harness user can open: its login stays in the runner's custody and reaches Claude Code only through the launcher's one-shot pipe; MCP credentials are served once over the turn's runner socket and the launch configuration holds none; and every entry created in `/private/tmp` is denied to the harness user by the kernel from creation (an inherited ACL entry; w4-harnessuser rounds 1 and 2, merged through cint-L50 for plan row #507). (3) A held secret value leaving through the agent: every value the runner holds (its own, the vault's, the root's MCP credentials, the harness login) is withheld from every reply and outbound text, and (plan #507) refused in every outward tool request before dispatch: a WebFetch URL or prompt, a WebSearch query, a Codex network read, an MCP or other outward tool's input, an unsandboxed command, and the shell network checkpoint's host, path, headers and body. A value once read stays held, and a held source that cannot be read refuses outward requests (fails closed). With no switch at all, no Claude Code tool turn runs: each is refused and answered text only (plan #473). A configured harness user that is not ready holds every launch; nothing runs as the operator's account. NOT closed, and stated below: files that every local user may read outside `/private/tmp`, and a credential the runner never held (another session's, in such a file), which no held-value check can recognise.

**Owner:** Echo (agent), as owner of the preview trial's tool admission. The cutover of each root is the desk's.

**The class:** the in-process file tools (Read, Write, Edit, Glob, Grep) are admitted by the PreToolUse hook (`tests/preview/tool-admission.mjs`), which decides on the realpath of the presented path and hands that resolved path to the harness. The decision happens at admission, not at open. If the filesystem on that resolved path changes between the hook's allow and the harness's open, the harness opens whatever is there then, which can lie outside the workspace. Review MF2 of unit w4-toolpaths and its round-2 review confirmed the class for both Read and Write with synthetic canaries. Only the agent writes into the conversation's volume, so such a change would have to be made by the agent itself, concurrently with its own file-tool call.

**How it is closed:** the harness runs as its own macOS user, `_instarharness` (uid 498), through `/Users/Shared/instar-harness/bin/harness-launch`, the one command the operator-granted sudoers rule names. Every open the harness or its file tools make is checked by the kernel as that user, at open, whatever path was admitted, so the race reaches only what that user can reach. That user has no access to the operator's home, so it can neither read nor write the operator's files: `~/.ssh`, the vault (`.instar/secrets`), every agent configuration under `~/.instar/agents`, the lanes and every preview root (journals, captures, runner state), the login keychain, and the operator-run login profile (`/Users/Shared/instar-preview-s2`). Verified as that user on the Studio on 2026-10-03 (`lanes/harness-user-PROGRESS.md`):

- through the launcher's probe, EACCES on read and on write for each path above;
- by the race itself, scheduled deterministically (`tests/integration/tool-turn-harness-user-live.test.ts`, case `race`): the real hook allows a workspace path, the path is swapped for a link to a canary in the operator's home, and the open happens. As the operator's account the open reads the canary; as the harness user Read and Write are refused, while an ordinary workspace file stays readable and writable;
- by a real tool turn on a throwaway root (case `turn`, record `tests/preview/fixtures/tool-turn/harness-user-2026-10-03/turn.json`) running as uid 498 with its full tool set, and by the stop (case `stop`: settled 201 ms after the stop, no process of the user left).

Whether a root is switched is decided from live state (`harnessReadiness` and `harnessGate` in `tests/preview/harness-user.mjs`), never from the flag alone. With no switch, the tool route refuses: `runToolTurn` records `harness identity unavailable` and answers text only before anything is reserved or launched, and the packet names no tools (`tests/preview/harness-user.test.ts`, plan #473 cases, both sides; `tests/preview/tools-default.test.ts` through the real launcher). With a configured user that is not ready, every launch is held until a later check is ready (`harnessGate`).

**Held values (plans #442, #473, #507):** the runner's held values are its own `INSTAR_SECRET_*` values, the preview vault's, the root's MCP credentials, and with the switch the custody login and any login Claude Code writes into the harness profile. Every value once read stays held for the runner's life (`createHeldSecrets` in `tests/preview/tool-turn.mjs`): a source that later changes, empties or becomes unreadable never drops it, and a source that cannot be read now is reported unavailable, which is distinct from a source that read and holds nothing. Each value is matched exactly and in its derived forms (base64, base64url, hex, URL and JSON escaping, a provider key without its kind prefix; case-folded for outward requests, since a host name is case-insensitive).

- **Replies and outbound text:** a reply carrying a held value is withheld exactly as credential-shaped text is (the credential notice is sent instead); the outbound check refuses any other text carrying one; recorded tool excerpts and the turn's admission record have them scrubbed. Proven on the recorded answer of update 969389800 (`tests/preview/held-cascade-replay.test.ts`).
- **Outward tool requests (plan #507):** the admission hook asks the runner's check (the turn's runner socket; the host checkpoint on a checkpointed route) about every string an outward tool call carries, property names included (review round 6: a value as a nested MCP property name was admitted before), before anything is done for it, a name lookup included, and refuses one carrying a held value; its record keeps a withheld marker instead of the input. The shell's network checkpoint checks each request's host, path and headers (a CONNECT authority before its name is resolved), a held git-fetch body whole, and a streamed body as it arrives, holding back the longest held form so no part of a value is forwarded before all of it is seen. Rule 95, this consumer's fail direction is closed: a held source that cannot be read (including a registered vault credential or an MCP-referenced credential whose sealed object cannot be opened when a fresh runner first reads it: `custodyHeldSources` in `tests/preview/tool-turn.mjs` reports it unavailable rather than empty, review round 6), a check that does not answer, an input over 1 MiB, or no check wired refuses the outward request. Ordinary web reads, searches and shell network are otherwise unchanged. Proven by replaying review round 5's synthetic reproduction through the real hook, the real turn configuration and the real turn socket (`tests/preview/held-egress.test.ts`: the login read through the swap race is refused in a WebFetch URL, raw, prefix-stripped and URL-encoded, in a WebSearch query and in a proxied GET or header; the ordinary neighbours are admitted; after the credential file is emptied the value is still refused; after it becomes unreadable outward requests are refused until it reads again; review round 6's replays: a held value as a nested MCP property name is refused while ordinary MCP inputs are admitted, and the production custody readers over real `createSecretCustody` hold a readable credential, clear an established absence, and report a corrupted sealed object unavailable so an outward request carrying it is refused), through the real egress proxy and curl (`tests/preview/egress-proxy.test.ts`, plan #507 cases: path, header, lowercased host name never resolved, streamed body cut, unwired and unreadable checks refused, an ordinary read forwarded), and at the host checkpoint (`tests/preview/session-admission.test.ts`, `held-egress.test.ts`).

This keeps a held value from leaving; it does not stop the harness reading a value that is already in its reach, and a value the runner never held is outside it.

**What stays true if the switch is off:** no Claude Code tool turn runs (above), so the race is not reachable through the tool route. The non-tool calls of the same profile (answers, reviews, summaries) still run as the operator's account, with no tools. The checks below hold in either state:

- **Sandboxed commands (Bash):** the kernel decides at open under the settings-derived Seatbelt profile, so no symlink, alias, `..` or changed spelling reaches past the boundary (`tests/preview/tool-paths.test.ts`). This holds with or without the switch.
- **File tools, before open:** every spelling the agent presents is decided on its realpath at admission, including `..` after an absent directory and dangling links. This is an early refusal, not a boundary at open.
- **This runner's own writers** (hygiene, not a closure of the race): the journal and the custody vault are AES-256-GCM ciphertext under the storage key, which lives only in the runner's environment. An MCP server's credential is given in the root's `mcp.json` as `{"secretRef": "<name>"}`; the runner opens it from custody at the turn and hands it once, over a private socket, to that server's launcher (`tests/preview/mcp-launch.mjs`; with the harness as its own user, the launcher's read-only copy beside the hook, and the socket in the harness area), so the launch configuration holds no SecretRef value. A credential written literally there in a recognised format is refused; an opaque literal no pattern recognises (for example a bare value after `--token`) is not detected and is copied into the launch configuration as written. The turn's admission record is scrubbed when the turn ends (each served value replaced by its SecretRef marker, recognised credentials redacted); while the turn runs the post hook writes into it, in plaintext, any credential a tool result carried, and a process death before the scrub leaves it there. `tests/preview/secret-at-rest.test.ts` checks the tested cases (a SecretRef value, an opaque and a recognisable credential in a tool result, the storage key) are absent from files under a driven root after a completed turn; it does not show every runner-written file is secret-free at every moment.

**What the race still reaches with the switch on (stated, not hidden):**

- **The harness's own area:** its own transcripts, its turn's admission state and its workspace. The harness must use these, so its user can read them. The Bash sandbox still denies the shell all of them except the workspace; only the file-tool race can reach them. The admission config is read-only to the harness by ACL. While a turn runs, the served MCP credentials are in the environment of the MCP servers, which run as the harness user; they are held values (above), so they cannot leave through a reply or an outward request.
- **Files every local user can read outside `/private/tmp`:** a separate user does not change what "readable by everyone" means. The `/private/tmp` entries are closed by the kernel (above), and on 2026-10-04 the 76 world-readable secret files found there were removed (lanes/harness-enable-PROGRESS.md). A credential of another session left world-readable elsewhere is not a value this runner holds, so the held-value check cannot recognise it; closing that is its owner's (write it private).

**Why not a code fix alone:** Claude Code sandboxes only Bash, and macOS refuses a sandbox nested inside one (`sandbox_apply: Operation not permitted`), so the file tools cannot be put under the kernel profile without losing the Bash sandbox. Replacing the built-in file tools with a sandboxed file server would reduce the agent's ability (images, PDFs, notebooks, Edit's read state), which the purpose forbids when a checkpoint can enforce the safeguard instead. A separate OS user is that checkpoint, enforced by the kernel at open.

## Plaintext secrets readable by the operator account that this runner did not write

Found on the Studio on 2026-10-03 by name and pattern only. No value was read out, and none was changed. With the switch on, the first three are out of the race's reach; the fourth is outside the tool runner.

- The Instar 1.x agent configurations under `~/.instar/agents/*/.instar/config.json` (Telegram bot tokens).
- An SSH private key under `~/.ssh/`.
- Files left in `/private/tmp` by other sessions holding the operator agent's API token and other credentials (now denied to the harness user by the kernel from creation; the ones found were removed on 2026-10-04).
- The older stage-1 and stage-2 runner (`tests/preview/agent.mjs`) keeps its captures in plaintext fixture stores (`tests/preview/composition.ts`, declared simulated custody); a credential typed to it would be stored in plaintext.

Done: the dedicated OS user, owning nothing of the operator's, with effective permissions checked as that user; the launch as that user behind `--harness-user`, decided from live state, every launch held while it is not ready; the tool route refused, loudly, with no switch (never the operator's account); the login in the runner's custody and MCP credentials served over the turn socket, never a file the harness user can open; `/private/tmp` denied to it from creation; every held value withheld from replies and outbound text and refused in every outward tool request and shell request before dispatch, never forgotten once read, failing closed when a held source cannot be read; the deterministic race test showing a protected read and a protected write refused at open; Part 17 §9 and `tests/preview/README.md` restated. Remaining for the owners of other world-readable credential files: make them private. If a root is found running a Claude Code tool turn as the operator's account, or an outward request is found carrying a held value, this record reopens.

**Multi-machine posture:** machine-local; each machine needs its own harness user (the root step) before its roots can switch, and until then its tool runner refuses tool turns and says so. The held set is per runner, read from that machine's own custody.
