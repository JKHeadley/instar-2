# File-tool race between admission and open (secrets floor)

**Status:** CLOSED for exactly two things, and nothing more is claimed. (1) The operator account's private files: closed by the kernel when the harness runs as its own macOS user (`--harness-user _instarharness`; desk unit harness-user, plan row #464, merged into w4-toolpaths for plan row #470), because every open is checked as a user that cannot read or write them. (2) The harness's own Claude login, which that user must be able to read: a value read through the race never leaves in a reply, because it is one of the exact values the runner holds, and a reply or outbound text carrying it (as written, JSON-escaped, or without its kind prefix) is withheld like credential-shaped text (plan #473). Without the switch, or with a harness user that is not ready, no Claude Code tool turn runs at all: each is refused and answered text only, never as the operator's account, and stderr at launch, the `status` answer (`Harness identity: REFUSED … (<reason>)`) and a notice under that answer name the reason (plan #473). NOT closed, and stated below: world-readable files of other local accounts' sessions under `/private/tmp`, and the harness reading (not sending) its own login. Today no live root has been switched, so live roots answer text only until each gets the harness profile's activation and its login (`lanes/harness-user/PLAN.md`, "The login").

**Owner:** Echo (agent), as owner of the preview trial's tool admission. The cutover of each root is the desk's.

**The class:** the in-process file tools (Read, Write, Edit, Glob, Grep) are admitted by the PreToolUse hook (`tests/preview/tool-admission.mjs`), which decides on the realpath of the presented path and hands that resolved path to the harness. The decision happens at admission, not at open. If the filesystem on that resolved path changes between the hook's allow and the harness's open, the harness opens whatever is there then, which can lie outside the workspace. Review MF2 of unit w4-toolpaths and its round-2 review confirmed the class for both Read and Write with synthetic canaries. Only the agent writes into the conversation's volume, so such a change would have to be made by the agent itself, concurrently with its own file-tool call.

**How it is closed:** the harness runs as its own macOS user, `_instarharness` (uid 498), through `/Users/Shared/instar-harness/bin/harness-launch`, the one command the operator-granted sudoers rule names. Every open the harness or its file tools make is checked by the kernel as that user, at open, whatever path was admitted, so the race reaches only what that user can reach. That user has no access to the operator's home, so it can neither read nor write the operator's files: `~/.ssh`, the vault (`.instar/secrets`), every agent configuration under `~/.instar/agents`, the lanes and every preview root (journals, captures, runner state), the login keychain, and the operator-run login profile (`/Users/Shared/instar-preview-s2`). Verified as that user on the Studio on 2026-10-03 (`lanes/harness-user-PROGRESS.md`):

- through the launcher's probe, EACCES on read and on write for each path above;
- by the race itself, scheduled deterministically (`tests/integration/tool-turn-harness-user-live.test.ts`, case `race`): the real hook allows a workspace path, the path is swapped for a link to a canary in the operator's home, and the open happens. As the operator's account the open reads the canary; as the harness user Read and Write are refused, while an ordinary workspace file stays readable and writable;
- by a real tool turn on a throwaway root (case `turn`, record `tests/preview/fixtures/tool-turn/harness-user-2026-10-03/turn.json`) running as uid 498 with its full tool set, and by the stop (case `stop`: settled 201 ms after the stop, no process of the user left).

Whether a root is switched is decided at launch from live state (`harnessReadiness` in `tests/preview/harness-user.mjs`), never from the flag alone. Not ready, or absent, the tool route refuses: `runToolTurn` records `harness identity unavailable` and answers text only before anything is reserved or launched, and the packet names no tools (`tests/preview/harness-user.test.ts`, plan #473 cases, both sides; `tests/preview/tools-default.test.ts` through the real launcher).

**The harness's own login (plan #473):** the runner's held values are its own SecretRef values, every string of 16 characters or more in the harness's `<config>/.credentials.json`, and the root's MCP credentials. The reply floor withholds a reply carrying any of them exactly as it withholds credential-shaped text (the credential notice is sent instead), the outbound check refuses any other text carrying one, and recorded tool excerpts and the turn's admission record have them scrubbed. Proven on the recorded answer of update 969389800 with a synthetic login value appended without its prefix (withheld, before Jev) and on the same answer without it (sent unchanged) (`tests/preview/held-cascade-replay.test.ts`). This keeps the value from leaving; it does not stop the harness reading its own login, which it needs.

**What stays true if the switch is off:** no Claude Code tool turn runs (above), so the race is not reachable through the tool route. The non-tool calls of the same profile (answers, reviews, summaries) still run as the operator's account, with no tools. The checks below hold in either state:

- **Sandboxed commands (Bash):** the kernel decides at open under the settings-derived Seatbelt profile, so no symlink, alias, `..` or changed spelling reaches past the boundary (`tests/preview/tool-paths.test.ts`). This holds with or without the switch.
- **File tools, before open:** every spelling the agent presents is decided on its realpath at admission, including `..` after an absent directory and dangling links. This is an early refusal, not a boundary at open.
- **This runner's own writers** (hygiene, not a closure of the race): the journal and the custody vault are AES-256-GCM ciphertext under the storage key, which lives only in the runner's environment. An MCP server's credential is given in the root's `mcp.json` as `{"secretRef": "<name>"}`; the runner opens it from custody at the turn and hands it once, over a private socket, to that server's launcher (`tests/preview/mcp-launch.mjs`; with the harness as its own user, the launcher's read-only copy beside the hook, and the socket in the harness area), so the launch configuration holds no SecretRef value. A credential written literally there in a recognised format is refused; an opaque literal no pattern recognises (for example a bare value after `--token`) is not detected and is copied into the launch configuration as written. The turn's admission record is scrubbed when the turn ends (each served value replaced by its SecretRef marker, recognised credentials redacted); while the turn runs the post hook writes into it, in plaintext, any credential a tool result carried, and a process death before the scrub leaves it there. `tests/preview/secret-at-rest.test.ts` checks the tested cases (a SecretRef value, an opaque and a recognisable credential in a tool result, the storage key) are absent from files under a driven root after a completed turn; it does not show every runner-written file is secret-free at every moment.

**What the race still reaches with the switch on (stated, not hidden):**

- **The harness's own area:** its login (`/Users/Shared/instar-harness/profile/config/.credentials.json`; with no keychain of its own Claude Code keeps it there; readable, but held from every reply and outbound text, above), its own transcripts, its turn's admission state and its workspace. The harness must use these, so its user can read them. The Bash sandbox still denies the shell all of them except the workspace; only the file-tool race can reach them. The admission config is read-only to the harness by ACL (the hook may add its record but not change or replace the runner's files). While a turn runs, the served MCP credentials are in the environment of the MCP servers, which run as the harness user.
- **Files every local user can read:** on the Studio on 2026-10-03 there were 23,379 world-readable files of the operator account under `/private/tmp` (other sessions' outputs; some hold the operator agent's API token). A separate user does not change what "readable by everyone" means. Their owners are other sessions of the operator account, not this runner; closing that needs those owners to write them private (umask), or a root ACL denying the harness user `/private/tmp`; neither is done, and this record does not claim it. This runner's own temporary artifacts that can carry a credential are already private to the runner and the harness user: the admission record and its slots (0600, in a 0700 directory with the two identities' ACL entries), the MCP launch configuration (0600, SecretRefs only) and the credential socket's directory (0700, traversable by the harness user alone besides the runner); the MCP values they carry are held values (above).

**Why not a code fix alone:** Claude Code sandboxes only Bash, and macOS refuses a sandbox nested inside one (`sandbox_apply: Operation not permitted`), so the file tools cannot be put under the kernel profile without losing the Bash sandbox. Replacing the built-in file tools with a sandboxed file server would reduce the agent's ability (images, PDFs, notebooks, Edit's read state), which the purpose forbids when a checkpoint can enforce the safeguard instead. A separate OS user is that checkpoint, enforced by the kernel at open.

## Closure

Done: the dedicated OS user, owning nothing of the operator's, with effective permissions checked as that user (not just an account created); the launch as that user behind `--harness-user`, decided from live state; the tool route refused, loudly, whenever that user is absent or not ready (never the operator's account); the harness login and the root's MCP credentials held from every reply and outbound text; the deterministic race test showing a protected read and a protected write refused at open, with an ordinary workspace file still readable and writable; Part 17 §9 and `tests/preview/README.md` restated. Remaining for the desk: give the harness profile its activation and its login, then switch each root (until then that root answers text only). Remaining for the owners of world-readable `/private/tmp` files: make them private. If a root is found running a Claude Code tool turn as the operator's account, this record reopens.

**Multi-machine posture:** machine-local; each machine needs its own harness user (the root step) before its roots can switch, and until then its tool runner refuses tool turns and says so.
