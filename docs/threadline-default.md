# Default Threadline connector

A configured worker receives Threadline alongside the default browser connector. It can send bounded text to a known peer, receive private peer data, and inspect the recipient's signed custody receipt. Unknown or unshared peers refuse. Peer text is data, never a human approval or an instruction source.

The smallest delivered slice is a local exchange between two installations. The transport uses the existing Threadline signing/encryption adapter over an encrypted filesystem spool. It opens no transport listener and buys no service. The per-claim MCP client uses the existing admission socket; identity keys remain in host custody. A `threadline_status` lookup never resends an earlier message. `accepted-by-transport` means encrypted staging succeeded; only the authenticated recipient's receipt establishes `durably-queued`. Neither state claims that a peer worker has answered.

Bootstrap occurs when the enrolled runner starts. It derives a stable identity from the installation storage key, stores the identity in existing custody before use, and publishes only its public keys and local inbox path in `threadline/public.json`. A missing or corrupt custody object refuses this connector while ordinary conversation remains available. Setup alone does not enroll a model login or activate the runner.

The installation owner signs a `threadline-team.json` record with version, principal, owner, expiry, withdrawn state, durability acceptance, and explicit peer entries. Each entry names a principal, signing/agreement public keys, inbox path, private topic and conversation. `threadline-owner.json` pins that owner's public key. The installer-side `instar2 threadline-bind` consumes the prepared signed record and owner pin from stdin, checks them against the onboarding owner and bootstrapped identity, and installs the exact zero-cost operation grants. This is an installer custody operation, never a worker tool. The agent/installation desk prepares enrollment; the person approves the private share, rather than editing files or running commands. Withdrawing the signed share or effect grant refuses the next operation.

A local-durable acceptance states the full causal-prefix requirement and permanent-machine-loss consequence. It does not change the existing P-08 profile or grant generic MCP effects. Before a send, the checkpoint records the full signed acceptance, parent authority, policy and exact input. The runtime additionally records a stable request identity in the encrypted journal. Duplicate requests do not resend, including after compaction or replacement of the host process. Calls reserve the existing claim's bounded allowance; messages are limited to 8192 bytes, peer bindings to 32, mailbox frames to 1024 and retained transport operation rows to 4096. Reaching capacity refuses new work without deleting accepted intake. A receive returns at most eight messages. Reuse its request identity after an uncertain response to recover the same delivery.

For an agent with several machines, the journal remains authoritative. Send preparation and accepted peer payloads survive its replication and compaction; the live runner's ownership and replication checkpoint runs before any frame or receipt is released. No missing replica lowers that demand. Identity derives from the installation key, not a machine name. Inbox paths are deliberately machine-local routing: moving a peer requires an updated owner-signed route. This slice does not add an internet relay, peer discovery, automatic responder scheduling, or interoperability with the legacy 1.x server protocol. It requires no second model provider; full native-loop connector parity remains the separate gap identified in census B.

Existing installations receive `threadline-bootstrap-1112` through the release updater. It replays the previous verified browser migration, adds the Threadline launch entry, and preserves existing Threadline configuration and an explicitly empty/revoked connector map. Exposing the tool grants no peer access. Enrolled peers still require the owner-signed private binding. The worker's actual launch resolves the built-in Threadline entry to the shipped credential-free MCP client, including the immutable hook copy for a confined harness user.

The implementation carries the automatic bootstrap and per-agent tool exposure behavior from JKHeadley/instar `db3ed6d3052cfcc24888b6c8bc86086abcfc2987`: `src/commands/server.ts:21745–21815`, `src/threadline/ThreadlineBootstrap.ts:993–1093`, and `docs/specs/threadline-mcp-local-http.md:76–110`. No legacy server implementation is copied verbatim. The new host glue is necessary because 2.0 already owns the crypto/receipt port, custody, journal and checkpoint; launching 1.x's server would create a second authority and storage owner. The existing adapter and its 46 contract tests are retained. The local spool and thin MCP client are new, bounded adaptations, not a claim of full 1.x networking parity.

`tests/preview/threadline-default.test.ts` drives two real setup roots, encrypted journals, signed installer enrollment, MCP subprocesses and the normal checkpoint. It covers exchange, signed receipts, private/unknown peers, secrets, stop, duplicate sends, journal compaction/restart and refusal on replica loss. It replays recorded summary, uncertain summary, undecided/unsure Jev, review and delivered-reply shapes as inert peer data. The corpus's empty row is an undelivered empty candidate, not evidence of a delivered empty bubble. A Studio live proof still needs enrolled single-provider workers, an owner-approved peer binding and routes, real worker-generated request/reply, member/guest scope checks, and a real two-machine ownership/replication exercise.
